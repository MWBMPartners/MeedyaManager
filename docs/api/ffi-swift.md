# UniFFI Bindings (macOS Swift)

> **(C) 2025-2026 MWBM Partners Ltd**

This page documents the UniFFI surface `crates/mm-ffi/src/uniffi_api.rs` exports for the macOS
SwiftUI app, how the Swift bindings are generated, and — the most important fact on this page —
that the shipped app does not currently call any of it.

## The headline fact: the macOS app does not link this today

- `macos/Package.swift` defines the `LIQUID_GLASS_AVAILABLE` compile flag unconditionally, but the
  `MM_FFI_AVAILABLE` flag that would enable the real FFI code paths is **commented out**:
  `// .define("MM_FFI_AVAILABLE") — uncomment when XCFramework is linked`.
- `macos/MeedyaManager/Bindings/MmCore.swift` is written with `#if MM_FFI_AVAILABLE ... #else ...
  #endif` around every method. With the flag unset, every single method — `version()`,
  `configPath()`, `scanDirectory(...)`, `getMetadata(...)`, `writeMetadata(...)`,
  `validateTemplate(...)`, `listKnownTags()`, and all five Test Mode methods — compiles to its
  `#else` branch, which returns realistic-looking but entirely synthetic stub data (a hard-coded
  sample track list, a `FileManager`-based directory walk instead of a real rename simulation, an
  `UserDefaults`-backed fake Test Mode flag, and so on).
- `ci-macos.yml` never links this either: it runs `cargo build -p mm-ffi --release` (producing a
  loose `libmm_ffi.dylib`) and then `swift build -c release`, but never sets `MM_FFI_AVAILABLE`
  and never builds the `MeedyaManagerFFI.xcframework` that `Package.swift`'s own header comment
  describes as the delivery mechanism. A repository-wide search for `xcframework` outside comments
  finds no workflow or script that actually produces one.

In short: the generated bindings below are real, complete, and committed to the repository, but
nothing in the current build wires them into the shipped macOS binary. Anyone reading
`MmCore.swift` should treat every method's live behaviour as the stub branch unless and until
`MM_FFI_AVAILABLE` is uncommented and an XCFramework is actually linked.

## How the bindings are generated

`crates/mm-ffi/src/bin/uniffi-bindgen.rs` is a three-line wrapper that hands off to UniFFI's own
CLI (`uniffi::uniffi_bindgen_main()`), enabled via the `"cli"` feature on the `uniffi` dependency.
The crate uses the proc-macro scaffolding approach (`uniffi::setup_scaffolding!("mm_ffi")` in
`lib.rs`), so bindings are generated by reading the **compiled `cdylib`'s** embedded metadata, not
a `.udl` file — the `mm_ffi.udl` file that also exists in `src/` is reference documentation, not
part of the generation path:

```bash
cargo build -p mm-ffi --release
cargo run -p mm-ffi --bin uniffi-bindgen -- generate \
    --library target/release/libmm_ffi.dylib \
    --language swift \
    --out-dir macos/MeedyaManager/Bindings/generated
```

**This is a manual step.** Unlike `include/mm_ffi.h` (regenerated automatically by `build.rs` on
every `mm-ffi` build — see `docs/api/ffi-c.md`), nothing in `ci-macos.yml` or anywhere else runs
`uniffi-bindgen`. The three files under `macos/MeedyaManager/Bindings/generated/` are committed
snapshots that a developer must regenerate and re-commit by hand after changing `uniffi_api.rs`,
`types.rs` or `callbacks.rs`. Treat them as potentially stale relative to the Rust source until
proven otherwise.

## Where the generated files live

| File | What it is |
| ---- | ---------- |
| `macos/MeedyaManager/Bindings/generated/mm_ffi.swift` | The Swift API itself — every function, struct, enum and protocol below (2,139 lines) |
| `macos/MeedyaManager/Bindings/generated/mm_ffiFFI.h` | UniFFI's own internal C scaffolding shim (glue for the Swift/C boundary). **This is not the same file as `include/mm_ffi.h`** — that one is the hand-maintained cbindgen header for the *Windows* C# P/Invoke surface; this one is UniFFI-internal plumbing private to the Swift binding and is not meant to be read or linked against directly (its own first line says "This file was autogenerated by some hot garbage in the `uniffi` crate. Trust me, you don't want to mess with it!") |
| `macos/MeedyaManager/Bindings/generated/mm_ffiFFI.modulemap` | The Clang module map that exposes `mm_ffiFFI.h` to Swift as the `mm_ffiFFI` module |

## Exported functions (19)

All of these are `#[uniffi::export]` in `crates/mm-ffi/src/uniffi_api.rs` and appear as top-level
`public func` declarations in the generated `mm_ffi.swift`. Functions that can fail throw
`MmFfiError` (a Swift `Error`-conforming enum generated from `types::MmFfiError`).

| Function | Signature (Swift) | Notes |
| -------- | ------------------ | ----- |
| `mmVersion` | `() -> String` | `CARGO_PKG_VERSION` |
| `configPath` | `() -> String` | Routed through `mm_core::config::app_config_dir()` — the single resolver (issue #212), not a direct `dirs::config_dir()` call |
| `configLoad` | `() throws -> String` | Loaded config as pretty JSON |
| `scanDirectory` | `(directory: String, template: String, recursive: Bool) throws -> [RenamePreviewFfi]` | Delegates entirely to `mm_core::renamer::simulate_rename` |
| `executeRenames` | `(previews: [RenamePreviewFfi]) throws -> UInt32` | Re-validates each preview via `renamer::execute_rename` immediately before moving — a stale `conflict: false` from an earlier scan is not trusted |
| `getMetadata` | `(path: String) throws -> [TagEntry]` | Multi-value tags joined with `"; "` |
| `writeMetadata` | `(path: String, tags: [TagEntry]) throws` | Routed through `mm_core::integrity::write_tags_safe` — the only path that honours Test Mode; an unmapped tag key now returns `MmFfiError.metadata` naming the key (issue #206) instead of silently doing nothing |
| `removeTag` | `(path: String, tagKey: String) throws` | Same integrity-guard routing as `writeMetadata` |
| `getAudioProperties` | `(path: String) throws -> AudioPropertiesFfi` | Duration/bitrate/sample-rate/channels/bit-depth; `0` where unknown |
| `validateTemplate` | `(template: String) -> ValidationResult` | Does not throw — invalidity is reported in the returned struct, not as an error |
| `applyTemplate` | `(template: String, tags: [TagEntry]) throws -> String` | Live-preview evaluation for the rule builder |
| `listKnownTags` | `() -> [String]` | Sourced from the TagRegistry (`config/tags.json5`), so user-defined custom tags appear automatically |
| `testModeEnabled` | `() -> Bool` | Fails open (`false`) if the manifest cannot be read |
| `setTestMode` | `(enabled: Bool) throws` | Does not itself commit/revert already-staged files |
| `testModeFileCount` | `() -> UInt32` | |
| `commitTestModeFiles` | `() throws -> UInt32` | Deletes originals, renames `_MeedyaManager` copies over them |
| `revertTestModeFiles` | `() throws` | Discards staged copies, leaves originals untouched |
| `startWatch` | `(directory: String, callback: WatchCallback) throws -> UInt64` | Spawns a background thread bridging `mm_core::watcher`'s channel to the callback; returns a handle ID |
| `stopWatch` | `(handleId: UInt64)` | Drops the watcher, closing the channel; a no-op for an unknown ID |

## Exported types

- **Records:** `TagEntry { key, value }`, `RenamePreviewFfi { source, destination, conflict,
  unchanged }`, `AudioPropertiesFfi { durationSecs, bitrateKbps, sampleRateHz, channels, bitDepth,
  isLossless, codec }`, `ValidationResult { isValid, errorMessage, warnings }`, `WatchEventFfi {
  kind, path, newPath }`.
- **Error:** `MmFfiError` — `.config`, `.io`, `.metadata`, `.rename`, `.ruleEngine`, `.watcher`,
  `.unknown`, each carrying a `String` message. Converted from `mm_core::error::MmError` at every
  FFI boundary (`types.rs`'s `From<MmError> for MmFfiError` impl).
- **Callback interfaces (`#[uniffi::export(with_foreign)]` traits in `callbacks.rs`):**
  - `WatchCallback` — `onEvent(event: WatchEventFfi)`, `onError(message: String)`. Implement this
    in Swift and pass an instance to `startWatch`.
  - `ScanProgressCallback` — `onProgress(current: UInt32, total: UInt32, path: String)`,
    `onComplete(errorMessage: String)`. **This one is dead code as of this commit**: it is defined,
    exported, and appears in the generated Swift bindings as a usable protocol, but no exported
    function anywhere in `uniffi_api.rs` accepts a `ScanProgressCallback` parameter — `scanDirectory`
    takes no callback. A Swift implementation of this protocol currently has nothing to attach to.

## Relationship to the C API

`uniffi_api.rs` exports 19 functions; `capi.rs` (the C/C# surface — see `docs/api/ffi-c.md`)
exports only 11. `executeRenames`, `getAudioProperties`, `startWatch`/`stopWatch`, and all five Test
Mode functions (`testModeEnabled`, `setTestMode`, `testModeFileCount`, `commitTestModeFiles`,
`revertTestModeFiles`) exist only on the Swift side — they have never been given a `capi.rs`
`#[unsafe(no_mangle)]` equivalent, independent of the 3 functions issue #208 tracks as merely
missing a C# `[DllImport]` (those 3 — `config_load`, `remove_tag`, `apply_template` — do exist in
`capi.rs`/`include/mm_ffi.h`; these 9 do not exist in the C API at all). If Windows parity with
macOS is ever wanted for renaming execution, audio properties, watching, or Test Mode, `capi.rs`
needs new functions added, not just new `[DllImport]` declarations against what already exists.
