# API Documentation

> **(C) 2025-2026 MWBM Partners Ltd**

This is the index for MeedyaManager's programmatic APIs — the interfaces other code (native UIs,
scripts, other Rust crates) calls into, as distinct from `help/`, which documents the application
for end users.

## Why there is no HTTP API here

MeedyaManager is **not a web application**. There is no OpenAPI/Swagger document in this
repository, and none is planned until there is something for it to describe:

- `mm-server` (the crate that will eventually serve media over HTTPS) depends on `axum`, `tower`
  and `tower-http`, and its `auth` and `streaming` modules contain real, unit-tested logic (JWT
  issue/validate, HTTP byte-range parsing). But a repository-wide search for `axum::Router`,
  `Router::new()`, `.serve(`, or `TcpListener::bind` returns **zero matches** — nothing in this
  workspace ever constructs a router or binds a socket. `routes.rs` defines handler *functions*
  (`handle_health`, `handle_login`, `handle_library`, `handle_search`, `handle_stream`,
  `handle_server_info`) that return typed `ApiResponse<T>` values and are exercised directly by
  unit tests, but they are never mounted on anything that accepts a network connection.
- The repository has **zero `.html` files**. There is no served UI and no JSON:API/REST surface a
  client can point a browser or an OpenAPI generator at.
- `meedya serve` (the CLI command that would start this server) reports exit code `3`
  (`NOT_IMPLEMENTED`) for exactly this reason — see [`cli.md`](cli.md).

Describing an HTTP API that does not exist would be worse than describing nothing, so this was an
explicit owner decision to defer OpenAPI/Swagger. What follows instead is documentation for the
three API surfaces MeedyaManager genuinely exposes today.

## The three real surfaces

| Surface | Consumed by | Documented in |
| ------- | ----------- | -------------- |
| Rust crate APIs (9 crates) | Other Rust crates in this workspace; anyone building against the workspace directly | [`rust-crates.md`](rust-crates.md) |
| C ABI (`include/mm_ffi.h`) | Windows — the WinUI 3 C# app, via P/Invoke | [`ffi-c.md`](ffi-c.md) |
| UniFFI bindings | macOS — the SwiftUI app, via generated Swift bindings (not currently linked — see below) | [`ffi-swift.md`](ffi-swift.md) |
| The `meedya` CLI | End users interactively; scripts and other processes via `--json` and exit codes | [`cli.md`](cli.md) |

Linux (`mm-gtk`) is not in this table: it is written in Rust and imports `mm-core`,
`mm-providers`, `mm-export` and `mm-server` directly as ordinary crate dependencies — no FFI layer
is needed because it never crosses a language boundary. See [`rust-crates.md`](rust-crates.md).

## How each surface is regenerated

| Artefact | Command | Runs automatically? |
| -------- | ------- | -------------------- |
| `cargo doc` HTML | `cargo doc --workspace --no-deps --open` | Yes — `.github/workflows/docs.yml` builds it (with `RUSTDOCFLAGS="-D warnings"`) on every push to `main` that touches `docs/**`, `help/**` or `crates/*/src/**` |
| `include/mm_ffi.h` (the C header) | Any build that compiles `mm-ffi`, e.g. `cargo build -p mm-ffi` | Yes — generated by `crates/mm-ffi/build.rs` via `cbindgen` on **every** build; the build fails outright if fewer than 11 `mm_ffi_*` prototypes come out, guarding against a repeat of issue #64 |
| Swift bindings under `macos/MeedyaManager/Bindings/generated/` | `cargo build -p mm-ffi --release` then `cargo run -p mm-ffi --bin uniffi-bindgen -- generate --library target/release/libmm_ffi.dylib --language swift --out-dir macos/MeedyaManager/Bindings/generated` | **No** — `ci-macos.yml` only runs `cargo build -p mm-ffi --release` and `swift build`; it never invokes `uniffi-bindgen`. The committed files under `Bindings/generated/` must be regenerated and re-committed by hand whenever `uniffi_api.rs`, `types.rs` or `callbacks.rs` change |
| `help/cli-reference.md` | Hand-written; not generated | N/A — owned by a different documentation package, not touched here |

The asymmetry in that middle column is real and worth remembering: the C header can never go
stale relative to `capi.rs` (a build regenerates it and fails loudly if the export count drops),
but the Swift bindings **can** go stale relative to `uniffi_api.rs` because nothing enforces
regeneration. Treat the committed `.swift`/`.h`/`.modulemap` files under `Bindings/generated/` as a
snapshot, not a guarantee.

## Consumer map

- **Windows C# (WinUI 3)** — `windows/MeedyaManager/Interop/MmCore.cs` calls into `mm_ffi.dll` via
  `[DllImport]` P/Invoke declarations that must match `include/mm_ffi.h` by hand. See
  [`ffi-c.md`](ffi-c.md) for the full function list and a verified mismatch between the two.
- **macOS Swift (SwiftUI)** — `macos/MeedyaManager/Bindings/MmCore.swift` is written to call the
  UniFFI-generated functions under `#if MM_FFI_AVAILABLE`, but that flag is commented out in
  `Package.swift` today, so the shipped app currently runs entirely on the `#else` stub branch.
  See [`ffi-swift.md`](ffi-swift.md).
- **End users and scripts** — the `meedya` CLI binary (`mm-cli`). Humans get coloured tables;
  `--json` gets machine-parseable output with documented exit codes. See [`cli.md`](cli.md).
- **Other Rust crates** — anything in `crates/*/src/lib.rs` that is `pub`, consumed either as a
  workspace path dependency (`mm-core`, `mm-providers`, `mm-export`, `mm-server`) or, for `mm-gtk`,
  as a manifest-path build outside the workspace. See [`rust-crates.md`](rust-crates.md).
